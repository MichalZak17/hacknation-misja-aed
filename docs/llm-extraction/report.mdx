# LLM extraction from OSM free text

The `osm-poland` source (OpenAEDMap, 18,297 nodes) is the bulk of our data, and most of its useful detail is in Polish
free text. The brief asks *where is the AED, is it accessible right now, does it work* — exactly what that text
describes. This report covers what the text contains, how well local LLMs turn it into fields, and which model and
setup to use. Everything here can be re-run with [scripts/llm_bench/](../../scripts/llm_bench/README.md).

## Summary

| | |
|---|---|
| **In use** | The shared **Qwen3.8-27B** that is already on the server, with the `strict` prompt and no evidence field: **117 of 120** test records fully correct, almost nothing invented. Built into every sync; the first full run took 62 minutes and added e.g. 2,211 vehicle AEDs and access conditions for 2,003 devices (see *In production*). |
| **If we need our own small model** | **Qwen3.5-4B** with the `strict` prompt: **106/120**, **~32 records/s** (the whole dataset in ~7 minutes), ~9 GB of weights, so it fits a 16 GB GPU. |
| **Biggest efficiency wins** | The `strict` prompt (more accurate *and* fewer tokens on every model); dropping the evidence field (~30–37% fewer output tokens, ~50% faster); one record per request with high concurrency (batching 10 records per request halved both speed and accuracy); sending only distinct, changed texts (18,297 → 13,395 once, then only changes). |
| **Don't use** | Qwen3.5-2B (makes things up), multi-record batching. Qwen3.5-9B and Qwen3-30B-A3B are slower than Qwen3.5-4B without being better. |

## What the free text contains

Snapshot of 2026-11-21:

| Tag | Records | Notes |
|---|---|---|
| `defibrillator:location` | 12,317 | Mostly Polish despite the missing `:pl`; 40 are English |
| `defibrillator:location:pl` | 5,172 | 481 differ from the generic tag; the connector keeps only `:pl` |
| `defibrillator:location:en` | 2,407 | Translations; 43 records have *only* English |
| `description` / `note` / `fixme` | 599 / 241 / 632 | Not mapped today (574 descriptions are dropped) |
| `opening_hours` | 6,781 | 4,136 are `24/7`; 252 don't parse as OSM syntax |

16,920 records have some text; there are **13,395 distinct inputs** once duplicates are removed, and only those need a
model.

Structure that can be recovered, by how often it appears:

- **AEDs carried in fire engines: ~2,160 records (12%).** "Samochód ratowniczo-gaśniczy" alone appears 766 times. Only 2
  are tagged `mobile=yes`, so their coordinates are the fire station's while the device leaves with the crew. This is
  the biggest gap for readiness and public maps.
- **Floor** stated in 1,187 texts; 576 of those have no `level` tag.
- **Indoor/outdoor** inferable for 236 of the 2,328 records with no `indoor` tag; ~116 contradict their tag.
- **Hours in prose** for 357 records with no `opening_hours` tag; the 252 malformed tags fall into a few fixable types.
- **Access conditions** (~350): kept in a porter's lodge or with security, key held by someone ("klucz u sołtysa"),
  siren button at the fire station, staff only, events only.
- **Capsules and cabinets** (~1,080): colour, alarm when opened, heated, lit; 39 on InPost parcel lockers.
- **Device counts** ("są 2", "dwa AED") in ~70 notes; **seasonal** availability in ~83.
- `fixme` is effectively a category list (exact location ~70%, opening hours, existence to confirm); 116 notes carry a
  data-acquisition date; 94 of 150 `ref` values are addresses.

**Connector bugs found on the way.** When the `location` tag is used as a fallback, 13 records get
`location_detail = "indoor"` / `"outdoor"` (and one gets `"wall"`). `description`, `note`, `fixme`, `phone` and `:en`
are dropped.

## How the benchmark works

**Fields extracted.** placement (vehicle / inside building / outside on a building / freestanding outdoor / unknown),
floor, opening_hours (OSM syntax), access conditions (8 types), seasonal, device count, enclosure (capsule / cabinet),
plus a short Polish position hint and, optionally, evidence quotes. All requests use vLLM's structured output against a
JSON schema, so every answer is valid JSON in the schema.

**Test set.** 120 distinct OSM records: 95 with harder text (hours, keys, floors, capsules, fire stations, staffed desks)
and 25 at random. Qwen3.8-27B pre-labelled them, then **every record was reviewed by hand**: 19 answers were corrected,
and 24 genuinely ambiguous records list other acceptable answers. Two numbers are reported per run:

- **Exact records**: all seven scored fields right.
- **Invented**: the model filled a field whose right answer is empty. These are the dangerous errors: a wrong "24/7" or
  a made-up access condition misleads a rescuer more than an empty field does.

**Prompts.**

- `rules`: field-by-field instructions.
- `fewshot`: the same plus 5 worked examples.
- `strict`: `fewshot` with the access rules rewritten as a decision list ("ask staff" only when the AED is kept *in*
  a staffed room, never inferred from the `access` tag) and 3 counter-examples.

**Hardware.** One A100 40 GB (vGPU, ~36.5 GiB usable), vLLM 0.34, one model at a time, prefix caching on.

## Results: speed

Throughput runs use the `strict` prompt without evidence on distinct real inputs. The small models ran in a benchmark
container with `--max-num-seqs 128`. The 27B was measured on the shared production server, which allows only 16
requests at a time; it would be faster with a higher limit, but that wasn't measured (its benchmark container took over
10 minutes to read the weights from this server's virtual disk and was stopped so production could come back).

| Model | Records/s | Inputs | Concurrency | Est. full run (13,395) | Out tok/rec | Failed |
|---|---|---|---|---|---|---|
| gemma-4-e4b | 43.53 | 2000 | 128 | 5 min | 65.5 | 0 |
| qwen3.5-2b | 40.83 | 2000 | 128 | 5 min | 62.0 | 0 |
| qwen3.5-4b | 31.67 | 2000 | 128 | 7 min | 61.4 | 1 |
| qwen3.5-9b | 23.11 | 2000 | 128 | 10 min | 68.5 | 0 |
| qwen3-4b-2507-fp8 | 20.37 | 2000 | 128 | 11 min | 73.5 | 0 |
| qwen3-30b-a3b-2507-fp8 | 15.48 | 2000 | 128 | 14 min | 73.9 | 0 |
| qwen3.8-27b-fp8 (production, max-num-seqs 16) | 3.56 | 500 | 16 | 63 min | 82.0 | 0 |

Speed findings:

- **One record per request beats batching.** vLLM already batches concurrent requests on the GPU. Packing 10 records
  into one request halved throughput (7.5 vs 14–16 records/s) and cut accuracy from 74 to 57.
- **Output tokens are the cost.** Dropping the evidence field cuts 29–37% of output tokens and speeds runs up by 48–60%.
  Accuracy moves between −4 and +3 exact records depending on the model (the 27B scored higher without it,
  Qwen3-4B-2507 lost 4). Input tokens are almost free: the shared instructions
  are cached.
- **Concurrency past 64 adds little on the small models** (Qwen3-4B: 21.7 records/s at 64, 20.4 at 128): the GPU is
  saturated.
- **Qwen3-30B-A3B is a mixture-of-experts model**, but with weights filling ~31 GB of the 36 GB, too little memory is left
  for parallel requests, so it ends up slower than the dense 9B.
- **Rare stuck generations.** Qwen3.5-4B once repeated text until it hit the length limit (1 of 2,000 records, a messy
  multi-line hours string). A retry, or handing the record to the 27B, covers it.
- Startup is 2.5–3 minutes per small model. A cold 27B load took over 10 minutes because of the virtual disk; from the
  memory cache it loads in seconds.

## In production

LLM extraction is part of every sync (`backend/integrations/enrichment/`, switched on with `LLM_ENABLED=true`). It uses
the shared Qwen3.8-27B with the `strict` prompt and no evidence field (`PROMPT_VERSION = "strict-v1"`), 16 parallel
requests.

- **Where it runs.** Between the diff and the write, outside the database transaction. Each connector says what the
  model reads (`text_input()`): OSM sends its free-text tags plus `opening_hours`, `level`, `indoor` and `access`, as
  benchmarked; other sources send their normalised location text. Records with no free text are not sent (the four
  small city feeds have none).
- **Only changed texts.** Answers are cached in `TextExtraction` by sha256(prompt version, model, input), and a record
  is sent only when its input key differs from the one stored with its last answer. A new prompt or model re-extracts
  everything, cache first.
- **Checked before use.** Out-of-range floors, device counts of 1, `opening_hours` that don't read as OSM syntax and
  unknown enum values are dropped. Answers are mapped onto Device fields (vehicle → `is_mobile`, placement → `indoor`).
- **Below every source.** The merge fills a field from `SourceRecord.inferred` only when no live source states it, and
  marks it `method: "inferred"` in `field_sources`. The admin UI shows these as **AI** with the source they came from,
  and each record shows the full answer, including the position hint, enclosure and device count.
- **Never blocks a sync.** One health check before calling; a run stops calling the model once most calls fail. Records
  without an answer keep their previous one and are retried on the next sync.
- **The OSM connector** no longer copies prose (e.g. "Całodobowo") into `opening_hours`; it stays in
  `opening_hours_raw` for the model to convert.

set `LLM_MODEL`, which changes every cache key and re-extracts.

## Limits of this benchmark

- **The answer key started from Qwen3.8-27B's output**, so its score is somewhat flattering. Every label was reviewed by
  hand, though, and the smaller models get no such advantage.
- **The `strict` prompt was written after looking at the 4B models' errors on this same set.** Its gain is measured
  in-sample. Its examples are synthetic, not taken from the set.
- **120 records is a small set.** Differences of 2–3 exact records between models are within noise.
- **Untested models.** Bielik (the Polish model family) needs a Hugging Face login, which this server doesn't have.
  Qwen3.5-35B-A3B FP8 (~36 GB) doesn't fit next to the KV cache.
